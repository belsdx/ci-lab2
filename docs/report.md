### 3.2. Код приложений

#### worker1 (`task1/worker1/app.py`)

```python
import os

DATA_DIR = "/var/data"
RESULT_DIR = "/var/result"
OUTPUT_FILE = os.path.join(RESULT_DIR, "data.txt")


def main():
    os.makedirs(RESULT_DIR, exist_ok=True)
    files = sorted(
        f for f in os.listdir(DATA_DIR)
        if os.path.isfile(os.path.join(DATA_DIR, f))
    )
    lines = []
    for name in files:
        with open(os.path.join(DATA_DIR, name), "r", encoding="utf-8") as fh:
            lines.append(fh.readline().rstrip("\n").rstrip("\r"))
    with open(OUTPUT_FILE, "w", encoding="utf-8") as out:
        out.write("\n".join(lines) + "\n")
    print(f"worker1: записано {len(lines)} первых строк в {OUTPUT_FILE}")


if __name__ == "__main__":
    main()
```

#### worker2 (`task1/worker2/app.py`)

```python
import os

DATA_DIR = "/var/data"
RESULT_DIR = "/var/result"
INPUT_FILE = os.path.join(DATA_DIR, "data.txt")
OUTPUT_FILE = os.path.join(RESULT_DIR, "result.txt")


def main():
    with open(INPUT_FILE, "r", encoding="utf-8") as fh:
        nums = [int(x) for x in fh.read().split() if x.strip()]
    if not nums:
        print("worker2: файл data.txt пуст, чисел не найдено.")
        return
    minimum = min(nums)
    cube = minimum ** 3
    os.makedirs(RESULT_DIR, exist_ok=True)
    with open(OUTPUT_FILE, "w", encoding="utf-8") as out:
        out.write(str(cube) + "\n")
    print(f"worker2: наименьшее число = {minimum}, куб = {cube}")


if __name__ == "__main__":
    main()
```

## 6. Ответы на контрольные вопросы

### 1. Что такое обмен сообщениями (messaging) и какие проблемы он решает?

Обмен сообщениями — это асинхронный способ взаимодействия компонентов
распределённой системы через отправку и приём сообщений через посредника
(брокера). Он решает проблемы: слабой связанности (decoupling) компонентов,
их независимого масштабирования, буферизации нагрузки при пиках,
устойчивости к отказам (если потребитель недоступен, сообщение ждёт в очереди),
а также разной скорости работы производителя и потребителя.

### 2. Что такое брокер сообщений? Какова его роль?

Брокер — это промежуточный сервис, который принимает сообщения от
производителей, маршрутизирует их и доставляет потребителям (или хранит до
момента доставки). Его роль — развязать производителя и потребителя во
времени и пространстве, обеспечивая надёжную, маршрутизируемую и
буферизируемую доставку.

### 3. Основные шаблоны обмена сообщениями.

- **Point-to-point (точка-точка):** сообщение доставляется одному потребителю
  из очереди.
- **Publish/Subscribe (издатель-подписчик):** сообщение копируется всем
  подписчикам.
- **Request/Reply (запрос-ответ):** поверх обмена реализуется RPC.
- **Work queue (конкурирующие потребители):** сообщения распределяются между
  несколькими потребителями для распараллеливания.
- **Dead letter (недоставленные сообщения):** обработка сообщений, которые
  не удалось обработать.

### 4. Определение RabbitMQ.

RabbitMQ — это популярный open-source брокер сообщений, реализующий протокол
AMQP и поддерживающий также MQTT, STOMP и др. Он принимает, маршрутизирует и
доставляет сообщения, поддерживая очереди, подтверждения, маршрутизацию и
надёжность.

### 5. Какой протокол лежит в основе RabbitMQ?

AMQP (Advanced Message Queuing Protocol), в первую очередь AMQP 0-9-1.

### 6. В RabbitMQ сообщения, принятые от продюсера, записываются…

…в очередь (queue), ассоциированную с точкой обмена (exchange) через
привязку (binding). Сначала сообщение попадает в exchange, затем маршрутизируется
в одну или несколько очередей.

### 7. Что такое точка обмена (exchange)?

Exchange — это логическая точка приёма сообщений от производителей. Она не
хранит сообщения, а маршрутизирует их в очереди согласно своему типу и
привязкам (bindings). Типы: direct, fanout, topic, headers.

### 8. Что такое Binding в RabbitMQ?

Binding — это правило (связь), соединяющее exchange с очередью. Оно задаёт
routing key (и, для headers-обменника, заголовки), по которым сообщения из
exchange направляются в соответствующую очередь.

### 9. Определение Routing Key.

Routing key — это строка-ключ, которую производитель указывает при публикации.
Exchange использует её для решения, в какую очередь направить сообщение
(в паре с привязками). Для fanout-обменника routing key игнорируется.

### 10. Процесс маршрутизации сообщения (по шагам).

1. Продюсер публикует сообщение в exchange, указывая routing key.
2. Exchange принимает сообщение.
3. Exchange по своему типу и привязкам определяет очереди-получатели.
4. Сообщение помещается в каждую подходящую очередь.
5. Брокер доставляет сообщение потребителю (при наличии) или хранит его.
6. Потребитель обрабатывает и подтверждает (ack) сообщение.
7. После подтверждения сообщение удаляется из очереди.

### 11. Для распараллеливания обработки сообщений — какой тип обменника?

Параллелить обработку по нескольким потребителям можно с **любым** типом
обменника, поскольку распараллеливание определяется очередью и
конкурирующими потребителями, а не типом обменника. Стандартный выбор —
**direct** (или default exchange), направляющий сообщения в одну очередь,
которую читают несколько потребителей (work queue).

### 12. Типы exchanges и их отличия.

- **Direct:** маршрутизирует по точному совпадению routing key.
- **Fanout:** рассылает сообщение во все привязанные очереди (игнорирует key).
- **Topic:** маршрутизирует по шаблону routing key с `*` (одно слово) и `#`
  (ноль и более слов).
- **Headers:** маршрутизирует по заголовкам сообщения, а не по routing key.

### 13. Продюсер отправляет сообщение …

…в точку обмена (exchange) с указанием routing key, а не напрямую в очередь.

### 14. Как предотвратить потребление устаревших данных?

Использовать TTL (time-to-live) для сообщений или очередей, а также DLX
(dead letter exchange), чтобы сообщения с истёкшим сроком автоматически
перемещались в отдельную очередь, а не оставались в основной.

### 15. По какому принципу устроены очереди — LIFO или FIFO?

FIFO (первым пришёл — первым ушёл), если сообщения имеют одинаковый
приоритет. При использовании priority queue порядок может меняться в пользу
более приоритетных сообщений.

### 16. Для чего предназначен Server (Broker/Node)?

Server/Broker (узел RabbitMQ) — это процесс, который хранит данные об
очередях, сообщениях, обменниках и привязках, маршрутизирует сообщения и
обслуживает клиентские подключения, обеспечивая доставку.

### 17. Назначение Virtual Host (vhost).

Vhost — это изолированное логическое пространство внутри брокера со своими
очередями, обменниками, привязками и правами доступа. Позволяет разделять
окружения и клиентов в одном экземпляре RabbitMQ.

### 18. Что такое подтверждение сообщений (ack/nack/reject)?

Подтверждение (acknowledgment) — это механизм, которым потребитель сообщает
брокеру, что сообщение обработано. `ack` — успешная обработка (сообщение
удаляется); `nack` и `reject` — обработка не удалась (сообщение можно вернуть
в очередь или отправить в DLX). Это гарантирует надёжную доставку без потерь.

### 19. Долговечные и временные очереди/сообщения.

- **Durable:** переживают перезапуск брокера (очередь сохраняется на диск,
  сообщения с delivery_mode=2 — persistent).
- **Transient:** не переживают перезапуск, удаляются при рестарте.
Durable-сущности обеспечивают восстановление данных после перезагрузки
брокера, transient — нет.

### 20. Dead Letter Exchange (DLX) и сценарии использования.

DLX — это обменник, куда перенаправляются сообщения, которые не могут быть
доставлены или обработаны (отклонены через nack/reject без возврата в очередь,
превышен TTL, превышена длина очереди). Используется для обработки
недоставленных сообщений, аудита ошибок, отложенной доставки (через TTL).

### 21. Priority Queue и как она работает.

Priority Queue — очередь, в которой сообщения доставляются согласно их
приоритету (целое число). Очередь создаётся с `x-max-priority`, а каждое
сообщение несёт `priority`. Брокер сортирует сообщения, отдавая сначала
более приоритетные.

### 22. Определение Apache Kafka и её философия.

Apache Kafka — распределённая потоковая платформа для хранения и обработки
потоков событий. Решает задачи потоковой передачи, буферизации и обработки
больших объёмов данных с высокой пропускной способностью. Философия
отличается от классических брокеров: Kafka — это распределённый
**журнал (log)** событий, который можно перечитывать (replay), а не очередь,
где сообщение удаляется после прочтения.

### 23. Архитектура Kafka: Broker, Topic, Partition.

- **Broker:** сервер Kafka, хранящий данные и обслуживающий клиентов.
- **Topic:** логическая категория/имя потока сообщений.
- **Partition:** физическое разбиение топика на части, каждая из которых — это
  упорядоченный, append-only журнал; распределяются по брокерам для
  масштабирования и параллелизма.

### 24. Consumer Group и её влияние на масштабирование.

Consumer Group — группа потребителей, совместно читающих один топик: каждая
партиция назначается одному потребителю группы, что позволяет
распараллелить чтение и масштабировать обработку. Несколько групп читают
топик независимо (каждая получает полный поток).

### 25. Реплика (Replica), Leader и Follower.

Replica — копия партиции для отказоустойчивости. **Leader** — реплика,
обслуживающая все чтения и записи; **Follower** — реплики, пассивно
синхронизирующие данные с лидера. При отказе лидера один из follower'ов
становится новым лидером.

### 26. ZooKeeper / KRaft и его роль.

ZooKeeper (и в новых версиях — встроенный KRaft) отвечает за управление
метаданными кластера: выбор лидера контроллера, хранение информации о
брокерах, топиках, партициях и репликах, координацию кластера. KRaft заменяет
ZooKeeper, устраняя отдельный компонент.

### 27. Kafka Streams против Consumer-приложений.

Kafka Streams — это библиотека для потоковой обработки данных (обогащение,
агрегация, соединение потоков, stateful-операции) поверх Kafka, с собственным
API и управлением состоянием. Обычный Consumer просто читает и обрабатывает
сообщения; Kafka Streams даёт готовые примитивы потоковых преобразований.

### 28. Фундаментальные отличия RabbitMQ и Kafka.

- **Модель хранения:** RabbitMQ — очередь (сообщение удаляется после ack);
  Kafka — журнал с retention (сообщения хранятся заданное время, replay).
- **Маршрутизация:** RabbitMQ — гибкая (exchange/binding/routing key); Kafka —
  топик + партиция (потребитель сам читает offset).
- **Состояние сообщений:** RabbitMQ управляет подтверждением и удалением;
  Kafka хранит offset потребителя отдельно и не удаляет сообщение после чтения.
- **Назначение:** RabbitMQ — маршрутизация/задачи; Kafka — потоки событий и
  аналитика в реальном времени.

### 29. Когда предпочесть RabbitMQ, а когда Kafka.

- **RabbitMQ:** сложная маршрутизация, гарантированная доставка отдельных
  сообщений, задачи/очереди, микросервисный обмен команд.
- **Kafka:** высокопроизводительные потоки событий, хранение и перечитывание
  истории, аналитика, стриминг, лог-агрегация.

### 30. Можно ли использовать RabbitMQ и Kafka вместе?

Да. Они дополняют друг друга: RabbitMQ — для синхронно-подобного обмена,
задач и сложной маршрутизации между сервисами; Kafka — для событийного
журнала, интеграции данных и потоковой аналитики. Например, сервисы общаются
через RabbitMQ, а события для аналитики публикуются в Kafka.
